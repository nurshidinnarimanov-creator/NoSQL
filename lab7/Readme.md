## 2. Описание предметной области и пользователей

Предметная область — **информационная система университета**.  
Основные сущности: студенты, дисциплины и преподаватели.

**Пользователи:**
- **Студент** — просматривает свои регистрации, пререквизиты выбранного курса, преподавателей.
- **Преподаватель** — видит список студентов на своих курсах, связанные дисциплины.
- **Администратор / учебный отдел** — анализирует загрузку курсов, цепочки пререквизитов, распределение студентов.

**Ключевые операции:**
- Чтение: поиск студентов курса, преподавателя курса, цепочки `REQUIRES`, количество записей.
- Запись: регистрация (создание `ENROLLED_IN`), изменение имени, удаление тестовой регистрации.

## 3. Таблица паттернов доступа

| № | Вопрос пользователя | Паттерн доступа | Тип операции |
|---|---------------------|-----------------|--------------|
| 1 | Какие студенты записаны на курс X? | `(s:Student)-[:ENROLLED_IN]->(c:Course)` | Чтение, 1-шаговый |
| 2 | Кто преподаёт курс X? | `(t:Teacher)-[:TEACHES]->(c:Course)` | Чтение, 1-шаговый |
| 3 | Какие курсы нужны для курса X (прямые)? | `(c)-[:REQUIRES]->(p)` | Чтение, 1-шаговый |
| 4 | Цепочка пререквизитов до 3 уровней | `(c)-[:REQUIRES*1..3]->(p)` | Чтение, variable-length |
| 5 | На какие курсы записан студент S? | `(s)-[:ENROLLED_IN]->(c)` | Чтение, 1-шаговый |
| 6 | Студенты курсов преподавателя T | `(t)-[:TEACHES]->(c)<-[:ENROLLED_IN]-(s)` | Чтение, 2-шаговый |
| 7 | Сколько студентов на каждом курсе? | `MATCH + count()` | Агрегация |

## 4. Обоснование графовой модели и сравнение с документной

Графовая модель выбрана, потому что ключевые запросы зависят от **цепочек связей**, а не только от атрибутов объектов:

- Цепочки пререквизитов (`REQUIRES*1..3`) — классический графовый обход.
- «Студенты курсов преподавателя» — двухшаговый путь `Teacher → Course ← Student`.
- Рекомендации и зависимости легко выражаются через отношения.

### Сравнение с документной моделью (MongoDB-стиль)

В документной модели пришлось бы хранить массивы `studentId` внутри `Course` или `courseId` внутри `Student`.  
При запросе «все студенты всех курсов преподавателя» потребовались бы несколько `$lookup` / join-подобных операций или денормализация с риском рассинхронизации.  

Обновление регистрации (добавление/удаление) требовало бы модификации массивов в нескольких документах.  
В Neo4j отношение `ENROLLED_IN` создаётся/удаляется атомарно, а обход остаётся естественным.

**Вывод:** для данного кейса графовая модель существенно удобнее именно из-за интенсивных обходов и многошаговых путей.

## 5. Схема графа

### 5.1. Узлы (labels и свойства)

| Label | Обязательные свойства | Уникальный идентификатор |
|-------|-----------------------|--------------------------|
| `Student` | `studentId` (int), `name` (string) | `studentId` |
| `Course` | `code` (string), `title` (string), `credits` (int) | `code` |
| `Teacher` | `teacherId` (int), `name` (string) | `teacherId` |

### 5.2. Отношения (типы и направления)

| Тип | Направление | Свойства / семантика |
|-----|-------------|----------------------|
| `ENROLLED_IN` | `(Student) → (Course)` | `semester` (string) — студент записан на курс |
| `TEACHES` | `(Teacher) → (Course)` | преподаватель ведёт курс |
| `REQUIRES` | `(Course) → (Course)` | курс A требует предварительного изучения курса B |

**Пример пути (повышенное задание):**  
`(c:Course {code:'ADV401'})-[:REQUIRES*1..3]->(p:Course)`

## 9. Изменение данных

Файл: `cypher/04_update.cypher`

```cypher
MATCH (s:Student {studentId: 1001})
SET s.name = 'Аружан Серикова (обновлено)'
RETURN s.studentId, s.name;
```

Контрольный `MATCH` подтверждает новое значение.

## 10. Безопасное удаление

Файл: `cypher/05_safe_delete.cypher`

1. **Сначала показываем** выбранную связь  
2. **Удаляем** только её (`DELETE r`)  
3. **Проверяем** отсутствие (пустой результат)

Удаляется тестовая регистрация студента 1005 на курс `PROG102`.

## 11. Анализ преимуществ, ограничений и масштабирования

**Эффективные запросы:**  
одношаговые `MATCH` по индексируемым свойствам (`code`, `studentId`) и короткие пути (1–2 шага).  
Variable-length path с ограничением `*1..3` приемлем на небольшом графе.

**Потенциально дорогие:**  
неограниченный `*` (без верхней границы) на графе с тысячами курсов;  
глобальный `count` без фильтров при очень большом числе узлов.

**Возможные избыточные связи:**  
прямое `REQUIRES` от `ADV401` к `DB201` при наличии пути `ADV401 → NOSQL301 → DB201`.  
В реальной системе можно оставить только прямые пререквизиты и вычислять транзитивное замыкание запросом.

**Ограничения и рост:**  
Neo4j хорошо масштабируется по чтению связанных данных.  
При десятках тысяч студентов основные индексы на `studentId`, `code`, `teacherId` остаются эффективными.  
Для аналитики по всему графу — APOC / GDS или вынос агрегатов.

## 12. Ответы на контрольные вопросы

**9.** Property graph — модель, в которой узлы и отношения могут иметь произвольные свойства (ключ-значение), а узлы группируются метками (labels).

**10.** Узел — сущность (объект), отношение — направленная связь между узлами, свойство — атрибут узла или отношения.

**11.** Labels группируют узлы по ролям (`Student`, `Course`) и позволяют эффективно фильтровать в `MATCH`.

**12.** `CREATE` всегда создаёт новый элемент; `MERGE` ищет совпадение по шаблону и создаёт только при отсутствии.

**13.** `MATCH` описывает графовый шаблон визуально: узлы в `()`, отношения в `[]`, направление стрелкой.

**14.** Направление отражает семантику («студент записан на курс») и делает запросы читаемыми.

**15.** Свойство — когда атрибут принадлежит только объекту; отдельный узел — когда сущность участвует в связях с другими объектами.

**16.** Двухшаговый обход показывает объекты, связанные через промежуточный узел (`Teacher → Course ← Student`).

**17.** Без ограничения глубины обход может стать экспоненциально дорогим на больших и плотных графах.

**18.** Графовая модель лучше документной, когда основные запросы — поиск по цепочкам связей, а не по атрибутам отдельных документов.
